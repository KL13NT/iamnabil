The Georgetown University Center for Contemporary Arab Studies (CCAS) holds a
vast and valuable archive spanning 50 years of history. This comprehensive
collection includes diverse media formats such as images, videos, documents,
flyers, links, and audio.

The project's technical challenge lay in striking a balance between user
experience for content editors, performance and ease of use, and
maintaining zero operational cost within a single, maintainable solution that
gave scholars easy access to half a century of valuable scholarship.

[View live](https://ccasarchive.georgetown.domains)

### Besides building the archive, my role also included:

- onboarding content editors and Georgetown's technical staff,
- presenting product demos and reviews,
- working with 8 stakeholders to ensure that their vision came true,
- and directing CMS content structure and strategy.

### The challenge

We needed a system that allowed searching, filtering, and general exploration
through multiple different views. These views range from the simple homepage
events rail to the complex archive page.

We needed dynamic content that content editors could easily change, possibly
through a CMS where they could easily distinguish assets, milestones, and pages.

### Solution

The traditional thought process of backend-frontend work doesn't work due to the
costs involved. Instead, I implemented a high-performance search
and filtering solution using Fuse.js, a lightweight fuzzy
search library, working inside the Astro framework for completely static,
yet interactive pages.

Content was managed through Storyblok and animations were implemented through
GSAP and custom CSS animations and transitions.

### Independent post-launch

And the best part? Non-technical staff, alums and students can continue to grow
the site without any support at all. When they publish new versions of the data,
the website rebuilds with the new data automatically.

### This architecture allowed me to:

- Use Storyblok's free tier for content management
- Employ Fuse.js for efficient searching and filtering
- Use Astro's Islands for an interactive, static site
- Preserve design's motion vision through Lenis and GSAP
- Keep bundles under 400 kbs and images optimised
- Near-instant navigation with Astro router prefetching

## Deep dive

Adding a backend wasn’t ideal because it would start accruing costs over time. I opted
for Storyblok’s free tier. Storyblok’s free tier was enough for our bandwidth
and storage for the life of the project, and I liked that it uses component-like
formats, which made it easy to compose things however I wanted.

I considered using Storyblok’s API and relying on its filtering capabilities, but that wasn’t ideal because the API has a very high cost ceiling for live use.

Instead, I chose Fuse.js, which is a lightweight, performant fuzzy search
library. I used it in [Badeel](https://badeel.wiki/), an ethical shopping
website that I worked on a while ago. It’s an offline-capable, open-source PWA
built with Solid and Fuse that has received over 200,000 page views to date. The
main goal was to let users search for products instantly, anywhere, even without
internet.

**Why Fuse**

Fuse is nice because it lets you specify specific keys to use as the index in
the dataset you supply. It uses that index and builds its search tree as
references to the objects you pass.

This lets me implement searching and filtering: when you don’t supply a query, you get the entire dataset back, which you can filter like a normal JS array. The dataset had only 500 entries, so it was easy to share the same JSON between the build process and the live frontend site.

This works by serialising component props into the HTML payload and then
hydrating it on the client. Astro does this out of the box, which is why
I love it so much.

**Interactive, yet statically generated**

Astro also supports what is known as the Islands architecture. This architecture lets you add fully interactive client-side components to completely static pages so that I can build filters and search components on static pages.

The main HTML response for pages that require the full dataset contains the data
embedded in the HTML. Other pages don’t include this inline data embedding since
they’re static and don’t need it.

**Results**

The following are the bundle sizes (uncompressed):

- The biggest page on the website, the archive page, comes in at around 2.4 megabytes. That includes the shared bits of the bundle like Lenis for smooth scrolling, the Split Text GSAP plugin, Fuse, Astro client router code, and Solid.
- Pages that don’t require the full dataset, like decades, come out to about half that.
- The timeline page fits in under 500 kilobytes.
- Each subsequent navigation after the initial page load comes to around 100 kilobytes thanks to Astro’s client router navigation.
- Links also have prefetching enabled, which enables near-instant navigation on click.

**How data flows**

Since each page template requires a different data shape, I used Astro’s
Collections API, a brilliant system that lets you define data you can consume
anywhere in your code. This approach is similar to Gatsby’s GraphQL layer, but
without the hassle and flakiness.

This let me create different data shapes to fit each page template’s needs. I
also passed all of this data through Astro’s Image optimisation API, letting me
perform programmatic image optimisation before the pages even attempt rendering.

**Accessibility**

I also focused on accessibility and worked with Roupen to get the most out of
the design. The website is fully functional with reduced animations, navigable
and consumable without JavaScript, and content structured so screen reader users
can make sense of the flow.

**Smooth backlinks**

One neat feature we wanted to add was the “View on Timeline” button present on
asset pages, which links from the archive page of an asset back to its decade on
the timeline. This was one of the biggest challenges in this project due to the
nature of how lazy loading works.

Each decade page has a huge set of assets, and therefore uses lazy loading. This
presented a problem for the “View on Timeline” button present on asset pages.
There’s no way to guarantee the position of assets that exist anywhere below the
fold. A lazy-loaded image doesn’t have any box attributes unless they’re
hard-coded.

This meant that when I clicked such assets to view them on their decade pages, I
would often land in the middle of nowhere on the page. Not to mention, since
it’s using smooth scrolling, lazy images present above the target asset would
begin loading and shifting the asset down, resulting in a lot more confusion.

This is where Astro’s Image API’s beauty really shines. All processed photos get
the final `width` and `height` values as part of their optimisation response. This
allowed me to set the `width` and `height` values on the rendered photos, which
guaranteed that they won’t pop in and shift the page while loading.

A trade-off of the smooth scroll is more data loading as the page scrolls to
the target asset, but I’d rather the user loads more of cached thumbnails which
aren’t large to start with snap into place and get confused about their position
on the page.

An additional safeguard that I could’ve added would’ve been a scroll-detection
mechanism that only attaches the `src` attribute of thumbnails when the user
isn’t scrolling too fast. Possibly through intersection observers and scroll
events.

**Related assets**

Another feature we wanted was related items. Related items on the inner
asset pages, related materials on each milestone’s section on the timeline. This
was fairly straightforward to implement using Astro’s Collections API.

Since I had all the data in a simple array format in the Astro Collections API
layer, I could simply filter through the array to find assets of the same decade
or category and cache the result.
